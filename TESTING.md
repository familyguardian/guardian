# Testing Guardian

Guardian's features depend heavily on OS integration (systemd-logind over D-Bus,
PAM curfews, `notify-send`, `loginctl`). Historically the test suite mocked all
of this, so tests stayed green while the real integrations broke. This document
describes the layered test strategy that exercises those integrations *for real*
- headlessly, so it runs in the Claude Cloud Dev Environment and in CI - and
reserves only the things that genuinely need a desktop for a documented,
externally-run E2E layer.

## Layers

| Layer | Marker | What it checks | Where it runs |
|---|---|---|---|
| L0 static | - | ruff / black / isort | anywhere + CI |
| L1 unit | - | pure logic, mocked I/O (per package) | anywhere + CI |
| L2 D-Bus contract | `dbus` | real bus + mock logind/notifications via dbus-next | Cloud + CI |
| L3 PAM curfew | `pam` | real `pam_time.so` via `pamtester`+`faketime` | Cloud + CI (root) |
| L3b systemd units | `systemd_units` | golden text of generated units (no running systemd) | *documented, not yet implemented* |
| L4 desktop E2E | `e2e` | real login/SDDM/termination per distro | *documented, external VM only* |

## Quick start

```bash
# One-time / per-session provisioning (idempotent): installs system deps
# (dbus, libnotify-bin, pamtester, libpam-modules, faketime), syncs uv, and
# smoke-checks every capability. Run automatically by the SessionStart hook
# (.claude/settings.json) in Claude Code on the web.
bash scripts/setup_testenv.sh
```

```bash
# L1 - unit tests (per package)
(cd guardian_daemon && uv run pytest)
(cd guardian_agent  && uv run pytest)
(cd guardianctl     && uv run pytest)
(cd guardian_hub    && uv run pytest)

# L2 - D-Bus contract tests (needs a session bus; runs headless)
dbus-run-session -- uv run pytest tests/dbus -m dbus

# L3 - PAM curfew tests (needs root for /etc/security/time.conf + /etc/pam.d)
uv run pytest tests/pam -m pam
```

The default unit selection excludes the heavier layers:

```bash
uv run pytest -m "not (dbus or pam or systemd_units or e2e)"
```

## L2 - D-Bus contract layer (`tests/dbus/`)

Runs guardian's real dbus-next client code (`SessionTracker.run()`,
`Enforcer.notify_user`, the agent's `NotifyUser`) against a **real** `dbus-daemon`
broker with a mock `org.freedesktop.login1` and `org.freedesktop.Notifications`
implemented in dbus-next (see `tests/dbus/conftest.py`).

Why dbus-next mocks rather than `python-dbusmock`: guardian subscribes to logind
signals via `manager.on_session_new(...)`, which dbus-next builds from the
object's **introspection**. python-dbusmock injects methods/properties into
introspection but **not signals**, so `on_session_new` would be missing. Serving
the mock with dbus-next gives correct signal introspection, keeps everything in
one interpreter (the uv venv), and needs no native build dependencies. The mock
session object deliberately exposes the real logind property shapes - notably the
`User` `(uid, object_path)` struct and a `Desktop` property - which is exactly
where the old MagicMock tests diverged from reality.

This layer connects to whatever `DBUS_SYSTEM_BUS_ADDRESS` /
`DBUS_SESSION_BUS_ADDRESS` point at; the fixtures set those to private buses, so
**no production code change was needed** to redirect guardian onto the mock bus.

## L3 - PAM curfew layer (`tests/pam/`)

`UserManager._generate_rules()` output is written to the real
`/etc/security/time.conf`, then `pamtester` evaluates the PAM **account** phase
(`acct_mgmt`) at controlled wall-clock times via `faketime`, asserting that login
is actually allowed inside the curfew window and denied outside it. The test PAM
service layers `pam_time.so` over a `pam_permit.so` fallback, mirroring how
pam_time sits on a real account stack (a no-match must not deny).

`test_curfew_enforcement.py::test_overnight_curfew_enforced` covers overnight
windows like `22:00-06:00`. These used to be emitted as the start>end range
`Wk2200-0600`, which pam_time does not treat as wrapping past midnight; the test
proves the (now fixed) splitting into `Wk2200-2400 | Wk0000-0600` is enforced on
both sides of midnight.

## Not yet implemented / external

- **L3b systemd unit golden tests** - cheap and in-cloud: snapshot the text
  generated by `systemd_manager.py` (extract the inline unit f-strings into pure
  render functions first) and optionally `systemd-analyze verify` offline. No
  running systemd required.
- **L4 desktop E2E** - cannot run in Claude Cloud (no systemd/logind/desktop).
  Author per-distro VM scenarios (Nobara / Bazzite / CachyOS) driven over SSH;
  `scripts/deploy_and_test.sh` is the natural basis. Distro risks to cover:
  Bazzite's immutable rpm-ostree `/usr` and the `dnf install` in
  `install_artifacts.py`; CachyOS/Arch having no `authselect`; per-distro SDDM
  PAM paths.

## Reliability fixes surfaced while building this

- `user_manager._generate_rules()` emitted overnight curfews (e.g. `22:00-06:00`)
  as the start>end range `Wk2200-0600`, which `pam_time.so` does not wrap past
  midnight, so the curfew silently failed to restrict logins. It now splits such
  windows into `Wk2200-2400 | Wk0000-0600` (matching `_is_user_in_curfew`'s
  existing overnight handling); the L3 PAM test enforces both halves for real.
- `policy.get_user_curfew()` (and its consumers `sessions.check_curfew()` and
  `user_manager._is_user_in_curfew()`) read a *different* curfew schema
  (`weekday`/`weekend` -> `{start, end}`) than the rest of the system produces -
  the config, IPC write-validation, CLI and PAM enforcement all use
  `weekdays`/`saturday`/`sunday` -> `"HH:MM-HH:MM"`. On any real config the
  reader therefore returned `None`, making both consumers inert (always-allow /
  always-false), and the daemon's `in_curfew=` log was meaningless. The unit
  tests only stayed green because the per-user fixtures used the phantom schema.
  All three now read the canonical schema with overnight-aware windows, and
  `_is_user_in_curfew` correctly reports the blocked period (the complement of
  the allowed login window) instead of being silently inverted.
- The same curfew checks also disagreed with PAM on *which users* have a curfew:
  `get_user_curfew()` read only the explicit per-user config, while
  `_generate_rules()` falls back to (and per-day merges) the **default** curfew.
  A user relying on the default curfew was therefore restricted by `pam_time` but
  reported as "no curfew" by `check_curfew()`/`_is_user_in_curfew()` (which also
  short-circuited on the explicit-only `has_curfew()`). Both now resolve the
  *effective* curfew through a single shared `policy.get_effective_curfew()` --
  the very helper `_generate_rules()` uses -- so the Python checks and the PAM
  rules can no longer drift. `has_curfew()` (and therefore `get_monitored_users()`)
  now reports the effective curfew too, so a user who relies on the default
  curfew is correctly treated as having one and is monitored.
- `storage.py` resolved the Alembic `script_location` relative to the process
  CWD, so DB migrations failed whenever the daemon/tests were launched from any
  directory other than `guardian_daemon/`. Now resolved against the daemon dir.
- `guardian_agent` / `guardianctl` / `guardian_hub` lacked a `[build-system]` and
  were not installable as packages (only importable by accident via CWD); plus
  stray outer `__init__.py` files shadowed the real inner packages and broke
  `python -m guardianctl`. Fixed so all four packages install cleanly.

## CI

`.github/workflows/ci.yml` runs L0 (lint), L1 (unit, matrix per package), L2
(dbus) and L3 (pam) on every push and pull request.
